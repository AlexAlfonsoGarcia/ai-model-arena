# AI Model Arena

> **Compare foundation AI models side by side.**

AI Model Arena is a full-stack web application designed to compare responses generated by different foundation AI models using the same user prompt.

The project is also designed as a **portfolio-quality demonstration of modern AI application development**, combining:

* Full-stack TypeScript development.
* Next.js and React.
* APIs from foundation AI model providers.
* Vercel AI SDK where appropriate.
* AI provider abstraction.
* Parallel AI inference.
* Response normalization.
* Latency measurement.
* Token usage tracking.
* Cost estimation.
* Automated testing.
* Git and GitHub workflows.
* Vercel deployment.
* Specialized Claude Code Skills.
* Project-specific Claude Code commands.
* AI application security practices.
* AI-specific testing.
* Architecture review workflows.

The project has two complementary goals:

1. Build a professional AI model comparison platform.
2. Build a specialized AI-assisted software development environment around the project using Claude Code.

---

# 1. Project Vision

The vision of AI Model Arena is to provide a simple and transparent interface where users can send the same prompt to multiple foundation AI models and compare the results.

Instead of interacting with one model at a time, users can see multiple responses simultaneously.

The application should eventually evolve from a simple model comparison tool into a broader platform for:

* LLM evaluation.
* AI model benchmarking.
* AI-assisted model selection.
* Automated response evaluation.
* Model performance analytics.
* Public model comparisons.
* Prompt benchmarking.

The MVP focuses exclusively on the core comparison experience.

The user should be able to easily compare:

* Model.

If one provider fails, the successful providers should still be displayed.


# 7. Provider Abstraction

The application must use a common provider abstraction.

Conceptually:

```typescript
interface AIProvider {
  id: ProviderId;

  generateResponse(
    prompt: string,
    options?: GenerationOptions
  ): Promise<AIResponse>;
}
```

The exact implementation may differ depending on the selected SDK architecture.

The important principle is that provider-specific SDK details must remain isolated.

The rest of the application should not need to know how OpenAI, Anthropic, or Google implement their APIs.

Adding a new provider should primarily require:

1. Creating the provider implementation.
2. Adding configuration.
3. Registering the provider.
4. Adding tests.
5. Updating documentation.

Provider-specific conditionals should not be scattered throughout the codebase.

# 9. API Contract

## Endpoint

```text
POST /api/compare
```

## Request

Example:

```json
{
  "prompt": "Explain artificial intelligence to a 10-year-old.",
  "models": [
    "openai",
    "anthropic",
    "google"
  ]
}
```

## Validation Rules

The backend must enforce:

* Prompt cannot be empty.
* Prompt maximum length: 10,000 characters.
* At least one provider/model must be selected.
* Maximum three providers/models per request.
* Only registered providers/models are accepted.

Never trust provider/model metadata sent by the client.

The server must resolve provider configuration from trusted server-side configuration.

---

# 10. Parallel Execution

Provider requests must execute concurrently.

Avoid sequential execution such as:

```typescript
await providerA();
await providerB();
await providerC();
```

Prefer a concurrency-safe approach such as:

```typescript
Promise.all(...)
```

or an equivalent implementation that allows individual provider failures to be isolated.

The desired behavior is:

```text
OpenAI       SUCCESS
Anthropic    ERROR
Google       SUCCESS
```

The API should return all available results.

A single provider failure must not prevent successful providers from returning their responses.

# 11. Normalized Response Model

The application should use a common response structure similar to:

```typescript
interface AIResponse {
  provider: ProviderId;
  model: string;
  content?: string;

  latencyMs?: number;

  usage?: {
    inputTokens?: number;
    outputTokens?: number;
    totalTokens?: number;
  };

  estimatedCost?: number;

  error?: string;
}
```

The exact type may evolve as the architecture develops.

Important rules:

* Do not fabricate token usage.
* Do not fabricate costs.
* Do not fabricate latency.
* If a provider does not return usage data, display that the information is unavailable.
* If pricing cannot be reliably calculated, display that cost is unavailable.
